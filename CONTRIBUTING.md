# Contributing to Immanueal1

First off, thank you for considering contributing to this open-source project! Contributions from the community help keep this project robust, well-documented, and production-ready.

---

## 📜 Code of Conduct

This project adheres to the [Contributor Covenant Code of Conduct](CODE_OF_CONDUCT.md). By participating, you are expected to uphold this code. Please report unacceptable behavior to [krishnakantgarhe@gmail.com](mailto:krishnakantgarhe@gmail.com).

---

## 🛠️ How Can I Contribute?

### 1. Reporting Bugs
Before creating a bug report, please check the [existing issues](https://github.com/Immanueal1/Immanueal1/issues) to avoid duplicates. When reporting a bug, use the **Bug Report Template** and include:
- Operating System & Version
- Vector/SVG viewer or browser details
- Clear step-by-step instructions to reproduce the issue
- Expected vs. actual behavior

### 2. Suggesting Enhancements
Feature requests and architectural suggestions are welcome! Use the **Feature Request Template** to explain:
- The problem your suggestion solves
- The proposed solution and alternative options considered
- Code / SVG / Documentation examples where applicable

### 3. Submitting Pull Requests (PRs)
Follow these steps to submit a Pull Request:
1. **Fork the Repository:** Create your own fork of `Immanueal1/Immanueal1`.
2. **Create a Feature Branch:**
   ```bash
   git checkout -b feature/amazing-feature
   ```
3. **Make & Test Your Changes:** Validate all Markdown files, SVG assets, and workflow files locally.
4. **Commit Your Changes:** Follow Conventional Commits guidelines (e.g., `feat: add new hardware schematic link`).
5. **Push to Your Fork:**
   ```bash
   git push origin feature/amazing-feature
   ```
6. **Open a Pull Request:** Target the `main` branch of `Immanueal1/Immanueal1` and fill out the Pull Request Template.

---

## 📝 Commit Message Guidelines

We follow the [Conventional Commits](https://www.conventionalcommits.org/) specification:

- `feat:` A new feature or component.
- `fix:` A bug fix or broken asset repair.
- `docs:` Documentation-only changes.
- `style:` Formatting, white-space, or visual SVG polish without code logic changes.
- `refactor:` Code refactoring without functionality changes.
- `ci:` Changes to GitHub Actions workflow files or automation scripts.
- `chore:` Maintenance tasks, dependency updates, or license updates.

**Example Commit Message:**
```
feat(assets): scale skill matrix vector icons to 1.55x with glow backdrop
```

---

## ⚙️ Coding & Documentation Standards

- **Markdown:** All `.md` files should be valid GitHub Flavored Markdown (GFM). Keep line length readable and use code blocks with language specifiers (`cpp`, `python`, `bash`, `html`, `yaml`).
- **SVG Assets:** SVG graphics must be valid, well-formatted XML with explicit `xmlns`, `viewBox`, `width`, and `height` attributes.
- **Git Branching Strategy:** Keep topic branches focused on a single logical change. Clean up merged branches promptly.
